# ADR-0006: Redis 기반 API 멱등성(Idempotency) 보장 설계

- **상태(Status)**: Accepted
- **영향 범위**: `module-common`, `module-api`

---

## 1. 배경 (Context)
네트워크 타임아웃으로 인한 클라이언트의 자동 재시도나 사용자의 결제 버튼 연속 클릭으로 인해 동일한 결제 승인·취소 요청이 서버에 중복으로 유입될 수 있습니다.
분산 락(`@DistributedLock`)은 동시 요청이 순차적으로 실행되도록 직렬화해 주지만, 첫 번째 요청이 이미 정상 완료된 뒤에 도착한 두 번째 재시도 요청까지 "중복 요청"으로 차단하거나 동일 응답을 보장해 주지는 못합니다.

따라서 클라이언트가 동일한 의도로 재전송한 요청은 서버에서 단 한 번만 실행되도록 **API 멱등성(Idempotency)** 보장 메커니즘이 필요했습니다.

---

## 2. 결정 사항 (Decision)
HTTP 요청 헤더의 `Idempotency-Key`와 Redis를 결합한 선언적 **AOP 어노테이션(`@Idempotent`)** 방식을 도입합니다.

1. **커스텀 어노테이션(`@Idempotent`) 정의 (`module-common`)**:
   - 컨트롤러 엔드포인트 메서드에 선언하여 멱등성 검증이 필요한 API만 선택적으로 적용할 수 있게 합니다.
2. **Redis 상태 머신 기반 중복 차단 (`IdempotencyAop`)**:
   - 요청 헤더에서 `Idempotency-Key`를 추출하고, 누락 시 `400 Bad Request` 예외를 반환합니다.
   - Redis(`Redisson`)에 키가 존재하지 않는 최초 요청이면 상태를 `PROCESSING`으로 원자적으로 선점(`setIfAbsent` / `trySet`)하고 만료 시간(TTL)을 부여한 뒤 비즈니스 로직을 실행합니다.
   - 이미 `PROCESSING` 상태인 동시 중복 요청이 들어오면 즉시 `409 Conflict` 예외를 반환하여 중복 실행을 차단합니다.
   - 정상 처리가 완료되면 상태를 `DONE`으로 갱신하며, 이후 동일 키로 재요청이 유입될 경우 중복 처리 없이 멱등하게 방어합니다.
   - 비즈니스 로직 실행 중 예기치 않은 예외가 발생하면 Redis 키를 정리하여 클라이언트가 동일 키로 안전하게 재시도할 수 있도록 합니다.

---

## 3. 결과 및 영향 (Consequences)
- **장점**:
  - `@Idempotent` 어노테이션 부착만으로 결제 생성·승인·취소·송금 등 핵심 금융 API에 일관된 멱등성 정책을 적용할 수 있습니다.
  - 분산 락(`@DistributedLock`)보다 앞단(Controller 진입 시점)에서 중복 요청을 걸러내므로 불필요한 DB 트랜잭션 및 락 경합을 줄여줍니다.
- **단점 및 고려사항**:
  - Redis 가용성에 의존하므로, 운영 환경에서는 Redis 장애 시 장애 전파 또는 폴백 정책을 함께 고려해야 합니다.
  - 추후 완전한 응답 재전송(Response Replay)이 필요한 경우, `DONE` 상태 저장 시 직렬화된 HTTP 응답 본문을 함께 캐싱하도록 확장할 수 있습니다.
